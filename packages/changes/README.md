# @perfoads/changes

The change engine: propose, check with Google, approve, apply once, read back, log and undo. The approval paths (elicitation, browser page, terminal) and the MCP tools live in `@perfoads/mcp-server`; the policy in `@perfoads/policy`. 13 change types (`src/types/`).

- **Lifecycle.** `proposed -> approved -> applying -> applied -> verified`, with `expired`, `rejected`, `stale` (the account changed before sending, nothing sent), `failed`, `in_doubt`, `verify_failed`, `resolved_by_user` (a person settled an unclear change with `markResolved`) and `abandoned` (still unclear 30 days after the last send). Every move is `UPDATE ... WHERE id = ? AND status = ?` inside `BEGIN IMMEDIATE` and must hit exactly one row; a store trigger refuses any move outside the table in `src/states.ts`.
- **Propose.** Input checked with zod (ids digits only, money as plain decimals in the account's currency, rounded to the currency's smallest unit), live "before" read incl. every campaign the change reaches (shared budgets, portfolio strategies), policy check, Google's `validateOnly` check on one atomic `GoogleAdsService.Mutate`, then stored with a server-built diff, a `diff_hash` (sha256 of the canonical change) and a 30-minute expiry.
- **Approve.** `markApproved(changeId, diffHash, via, by)` is for the approval paths only. It refuses an expired change, any hash that is not the stored one, and a row whose recomputed hash differs. A store trigger refuses `proposed -> approved` without who, how and when, and freezes everything the approval view showed. `ChangeView.version` is the hash: a version id, never proof of approval.
- **Apply.** On Google Ads test accounts, or on accounts the policy lists under accounts.write (read live). Earlier unclear changes to the same item are re-checked first (still unclear = refused). Policy asked again, claim `approved -> applying`, then the same change is planned again from live data: any difference in what the approval showed (values, affected campaigns, the budget a campaign turns on, currency) = `stale`, nothing sent. Sent once with `MUTABLE_RESOURCE`, then a confirming read with short retries (`verified` or `verify_failed`). One apply has a 200 s deadline; less than 130 s left before a send (two 60 s attempts for a 401 resend + the token refresh) = "not sent".
- **One writer per item.** Each change stores the keys of every item it touches (the budget or strategy and every campaign on it). The claim refuses ("blocked", still approved, try again later) while another change to any of those items is being applied or was sent less than 10 minutes ago and is still unclear.
- **Busy.** A write Google refused as busy (429, RESOURCE_TEMPORARILY_EXHAUSTED) applied nothing. CONCURRENT_MODIFICATION means someone else wrote the item at the same moment: `stale`, never re-sent. The engine waits (Google's delay or 2 s / 5 s, 30 s in total), re-reads, and sends again only if the account is still exactly as approved; otherwise `stale`. At most 2 re-sends. The client itself never re-sends a write.
- **Unclear answers.** Timeout, reset, 5xx: `in_doubt`, never sent again. New values read -> `applied` -> read-back. Old values: `failed` only 10 minutes after the last send AND with no change to that resource in the change history (account time zone, from the last send - 62 min to now, sends up to 28 days old); otherwise it stays `in_doubt` ("probably did not land - will re-check"). A failed read never counts as a reading. `reconcile()` at startup does the same for changes left in `applying`.
- **Undo.** A new change of the same type from the stored before values, with its own approval, for 30 days, refused when the account changed since.
- **Log.** Append-only `audit_log` with a hash chain; refusals (hash mismatch, not a test account, policy, earlier unclear change, undo) are logged too, with actor and via; `verifyChain()` and `exportHead()`. An edit or a removed row in the middle breaks the chain; a cut-off tail shows only against a head exported earlier. It does not stop someone who rewrites the whole file.
- **Policy.** `PolicyCheck` is the seam for the policy engine (`@perfoads/policy`). It is asked at propose (with this account's claims of the last 24 hours), before the claim, and again inside the claim transaction, so rolling limits are serialised with every other claim. `autoApprove` lets the policy approve an auto-tier change itself (`approved_via` `policy_auto`). The default, `READ_ONLY_POLICY`, refuses everything.

Change types: `update_budget`, `update_campaign_status` (ENABLED / PAUSED only, never REMOVED), `update_bidding` (see the header of `src/types/updateBidding.ts` for what is supported).
